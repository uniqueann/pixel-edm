# 发信活动页 UI / UX 打磨与验收

日期：2026-10-29。开发分支：`design/campaigns-ui-polish`。

## 页面与核心流程分析

本轮依据现有路由、组件、权限判断和本地浏览器实测进行选择，没有使用线上访问频次或转化率数据。

核心流程为：登录并进入工作区 → 在设置页准备署名、联系地址及发信通道 → 添加或导入客户并确认订阅 → 准备邮件模板 → 新建活动草稿 → 计算收件人、补全变量并预览 → 确认并锁定名单 → 管理员正式发送 → 查看统计、投递明细或导出 CSV。

| 页面 | 在流程中的作用 | 本轮判断 |
| --- | --- | --- |
| 总览 `/dashboard` | 检查准备项、查看最近活动和动态 | 已有下一步清单，可以把用户引导到业务页面 |
| 客户及导入 `/contacts` | 管理订阅、标签、导入校验与归档 | 列表结构明确，导入有独立的校验流程 |
| 模板 `/templates` | 准备内容、插入变量、预览和管理模板 | 分类和卡片网格已形成稳定结构 |
| **活动 `/campaigns`** | **连接内容、受众、确认、发送和结果查看** | **状态和操作最多，直接影响核心任务，优先优化** |
| 设置 `/settings` | 配置工作区、署名、通道与套餐 | 是发信前提，但涉及较多配置和套餐边界，本轮不扩展 |
| 团队、日志、帮助 | 协作、审计、配置指导 | 属于支持性流程；保留现有入口及角色限制 |

实际查看了总览、客户、模板、活动的桌面页面，以及活动列表和编辑弹窗的手机页面。

## 为什么优先选择活动页

活动页集中承接整个发信流程，用户既要识别草稿、已确认及发送结果，又要判断当前可做的操作。原界面有三个主要问题：

1. 新建按钮与筛选控件混排，搜索框另起一行，创建和查找的层级不够明确。
2. 卡片中的说明文字垂直间距较大；编辑、预览、归档权重接近；混合状态下，活动信息、操作和统计相互挤占空间。
3. 编辑弹窗将基础配置和变量连续堆叠，变量名称与模板语法视觉权重接近，桌面空间没有充分利用。

## 实施内容

- 保留暖灰底色、深蓝主色、现有字体、Lucide 图标及共享 Button、Badge、Card、Dialog。
- 标题与活动数量相邻，新建入口独立于筛选；搜索、显示范围和状态筛选组成统一工具栏，并提供可见标签。
- 将卡片分为活动信息、投递摘要、操作区域。预览、正式发送和统计查看分别对应活动的不同阶段；归档采用较低视觉权重。
- 沿用现有语义色展示草稿、已确认、已完成及异常状态，状态文字仍保留，不依赖颜色表达。
- 用图标和紧凑间距组织模板、受众及时间；数字采用等宽数字排版，长名称正常换行。
- 草稿弹窗用语义化 `fieldset` 分组；桌面采用双列，手机采用单列；模板语法作为次级信息。
- 本页手机搜索、筛选、卡片操作和编辑控件至少 44px 高。按钮仅对颜色、边框和焦点阴影做过渡，避免断点切换时尺寸动画。
- 编辑操作栏随表单自然滚动，防止手机键盘缩小时遮挡正在输入的字段。
- 样式限定在 `campaigns.module.css`，不修改全站样式或共享组件。

## 业务不变性

没有修改 Server Actions、RPC、数据库迁移、发送门禁、角色权限、配额、统计口径、轮询、表单提交参数或未保存保护。

使用 TypeScript AST 比较修改前后的客户端逻辑：组件主返回之前的状态与函数、辅助函数，以及所有事件处理、禁用条件和值绑定均一致。变化限定在 JSX 结构、样式、图标及辅助语义。

- 视觉实测：320 / 390 / 820 / 1440px，浅色与深色，草稿、已确认和已完成的混合列表、编辑弹窗及投递统计。

- 筛选加载、无匹配结果及模拟保存失败均已检查；保存失败时错误提示和原有输入正常保留。
